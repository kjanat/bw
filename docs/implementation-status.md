# Implementation scope and evidence

The target is an independent TypeScript implementation of the Bitwarden CLI's
Vaultwarden-supported behavior, with a reusable library and DreamCLI frontend.
This file lists the full target. Each unfinished row names work still to do.

The reference command surface is captured from `/usr/bin/bw` 2026.10.0 in
[the command inventory](reference/bw-cli-2026.10.0.json). Server-specific behavior
is checked against Vaultwarden handlers, not inferred solely from the official
client. Bitwarden cloud-only flows need tests against Bitwarden servers.

CLI list/get and Serve item searches use `searchItemsBasic`, matching the pinned
per-term search across item name, UUID prefix, display subtitle, login URI
hostname, and notes. URI paths, regex-match URIs, passwords, and custom fields
are not search targets. Terms may match different fields on the same item. A
query erased by accent normalization returns no matches rather than every item.

Completion requires library and CLI tests for each supported operation, real
Vaultwarden evidence for server mutations, a documented disposition for every
reference command, and removal of partial-reader restrictions. A green subset
of tests does not establish full completion.

Surface audit against the pinned 2026.10.0 command inventory: 29 reference root
command names are available locally under the same spelling (`help` is
DreamCLI's built-in route and is integration-tested). DreamCLI's built-in
`completions` subcommand generates the shell scripts; its spelling and
positional shell argument differ from the reference CLI's `completion
--shell` form. Every non-help long-option name is present across all 29
command-specific help records. The local CLI also has wrapper and
Vaultwarden-specific options. These are command-surface measurements, not a
behavioral-completion percentage.

The item visibility path also evaluates enabled organization policy type 15
(`RestrictedItemTypes`) from sync data. Its defaults and cross-organization
allow-list behavior follow the installed bw source; fixtures cover personal and
organization-owned items. CLI live tests on Vaultwarden 1.36.0 and 1.37.4 verify
a non-admin member cannot create or read a restricted card, or see it in `list`;
its card and attachment are absent from personal ZIP export. An additional
1.37.4 live assertion verifies direct attachment reads fail before an output
file is written. Service regressions also block direct item reads and policy-
hidden attachments via the exact-ID helper before any attachment request. The
fixture uses the flat policy payload on 1.36.0 and the nested payload on 1.37.4.

Mutation guards now also follow the source for restricted item creation, editing,
and deletion; deleted-item edit rejection; archive state checks; and organization
collection deletion GUIDs. These have focused pre-request regression coverage.

Server capability evidence: Vaultwarden
[`src/api/core/sends.rs` at 58a980f](https://github.com/dani-garcia/vaultwarden/blob/58a980f850464f7d9cdc99a765df36f0a3308b91/src/api/core/sends.rs)
declares text/file creation, management, password removal, anonymous access, and
signed file-download routes. `create_send` explicitly rejects an `emails` value
with “Sends with email verification is not supported”. Text/file Send behavior
is implemented in `SendService` and `receiveSend`; email verification is a
server limitation. Legacy body-based access is implemented and live tested on
1.36.0; broader server-version and reference-client coverage remains required
work.

Recovery-code login now follows the pinned Vaultwarden identity handlers: provider
8 can be explicitly selected even though it is absent from the enrolled providers
in a challenge. Password and SSO grants normalize recovery codes to lowercase
without spaces, including for 1.36.0, which requires that canonical form. Other
factor tokens are passed with their original contents. Interactive `--method 8` entry uses
the hidden reader and explains that recovery disables the account's two-step
login methods. Provider discovery accepts both Vaultwarden's string IDs and
numeric IDs.

The isolated recovery regression passed against the pinned 1.36.0 and 1.37.4
containers using the built production library. It verifies the unadvertised
provider, spaced uppercase recovery input, vault decryption, and removal of the
account's second factors. SSO request behavior has focused transport coverage;
the compiled Node prompt host has PTY coverage for hidden recovery entry and
terminal restoration. These checks do not establish the full compatibility
matrix or live SSO recovery coverage.

Attachment-ID selection has live regressions on Vaultwarden 1.36.0 and 1.37.4:
the PBKDF2 cases cover both versions, and the 1.37.4 case also covers Argon2id.
Each uploads attachment A, uploads attachment B with A's ID as B's filename,
then downloads A by ID and compares the exact bytes. In the 1.37.4 fixtures,
pinned `bw` 2026.10.0 returns B's marker bytes for a request using A's ID; both
KDF runs record that difference explicitly. The local client returns A's bytes.
The latest 1.37.4 run also exercised the direct restricted-attachment denial.
Service and CLI fixtures cover the same collision and ID-only retrieval
behavior.
